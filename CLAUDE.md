# LLM PlayGround

A web playground for LLM providers and routers, plus a place for small LLM-based experiments such as games. Live at https://hkarn.github.io/LLM-PlayGround/. Forked by copy from requesty-tester. Endpoints so far: Requesty, OpenRouter, LLM Gateway (hosted), a self-hosted LLM Gateway and a custom OpenAI-compatible URL.

- Run: `node server.js` (Node 18+, no dependencies), then open http://127.0.0.1:3000. It reads `.env` next to it (variables already set in the environment win), as `docker compose` does. Docker: `docker compose up`.
- Endpoints are settings files, one per provider: `public/providers/<id>.json` (order in `providers/index.json`), loaded at start-up by `loadProviders()` into `PROVIDERS` in `public/js/core.js`. Each has `label`, suggested `baseUrl`, `modelsPaths`, `keyEnv`, `keyHint`, `keyOptional` (the page may load models and send without a key: Custom only), `signup`, `server.domain`, `unsupported` tabs, per-tab `endpoints` overrides (`path` and `base: {replace: [pattern, with]}` read by `ep(kind)`, and the request/response template keys read by `adapter.js`), `suggest` lists, `guide` (the provider box on the Welcome page: setup `level` 1-4, `ease`, `summary`, `steps`, `good`, `watch`) and `speechVoices` (a voice-list file in `providers/`, e.g. the shared `speech-voices.json`), `modelFields` (per tab, fills the page's own model fields such as `supported_durations` or `supported_frame_images` from where that provider keeps them: a path, or `{if, value, else}`; applied in `core.js` when models load; LLM Gateway's video models) and `required` (per tab, fields its API needs, which the tester then offers without "default"; LLM Gateway's video `duration`, sent as `seconds`); comments go in `_notes`. Hardcoded, provider-specific data belongs in these files, not in code. Greyed tabs: Requesty rerank/video; Custom decision/rerank/video (no OpenAI standard). A new provider is a new file plus its id in `index.json`. The first provider in `index.json` that works on the page (OpenRouter: Google sign-in, credit, key, every model on) is the default for a new visitor; a saved choice wins. The page opens on the Welcome page (`providers-guide.js`, tab and hash still `providers`; its tab button is hidden and the logo is its link, underlined with `aria-current` while it is open): what the site is, getting started, cards for every app in `APPS` (an app with `video: true` is tagged with the providers that have `videoModels`) plus the API tester and Filter models, privacy in brief, then one wide box per provider with its setup, sign-up and referral links. Requests and answers go through `public/js/adapter.js`: `send(kind, input)` fills the endpoint's `request` template (shared OpenAI-standard shapes in `providers/openai-standard.json`, named as `templates` in `index.json`; a provider's `endpoints.<kind>` replaces keys of it) and `read(kind, resp)` maps the answer to the app's own terms (`text`, `images[]`, `usage`, …) through its `response` map. Template rules are in the `_notes` of `openai-standard.json`. Every kind goes through it: chat, decision, embeddings, rerank, image, imageEdit, video, speech and transcription (all tester tabs, Draw the DreamGen Scene, AI Group Chat). A File inside an input is sent as a data URL in JSON bodies (shown as a placeholder); an async job's follow-up GETs are `poll`/`content` path templates sent with `follow(kind, step, vars)` (video). Never build a provider's wire format in an app.
- Model filter (the Filter models tab in the top bar, `#models`, `ui/model-filter.js`, kept per provider in localStorage as `modelfilter_<provider>`): a providers list matched exactly against the maker before the `/` (a leading `~` ignored) and a models list matched as a prefix of the name, or of the whole id when the row has a `/`; case ignored, empty lists match everything. Every model list reads `visibleModels()`/`modelsIn()` in core, which apply it, so a new list must use those rather than `state.models`.
- Curated models (`public/providers/curated-models.json`, named in `index.json` as `curated`, loaded into `CURATED` in core): one list for every router, per kind (`chat`, `image`), entries `{ name, label, price, note }`. The picker's **curated** checkbox shows the entries found on the key (entries with `draft: true` are unsure candidates, listed last and marked "draft"), matched by the model's own name (the id's last part, ignoring case, `.` vs `-`, `@region`, `:variant` and a trailing date tag; a model of the picker's kind wins). It is offered only where a picker has `data-curated` (the tools; `"on"` starts it ticked) and remembered per kind; the API tester tabs, which are for trying any model, don't show it. Add a model only after a real run; `price` is relative (`$`–`$$$$`). Draw the DreamGen Scene sends reference pictures as JPEG (`asJpeg` in `ui/frame-image.js`): in tests AVIF and WebP were each refused by some models, JPEG by none.
- Dropdowns follow the model (`setupModelOptions`): model metadata first, then the provider's `suggest` list (`false` = not supported), then the options in `index.html`. Disabled fields are never sent (`str`/`num` skip them). Add hardcoded suggestions only where no API list gives the choices. The base URL field is editable; each provider keeps its own key and edited URL in `localStorage`.
- `server.js` serves `public/` and proxies `/api/*` to the `X-Upstream-Base` header the page sends. It reads the same provider files: a provider with `server.domain` and `keyEnv` gets a server key from that env var (`REQUESTY_API_KEY`, `OPENROUTER_API_KEY`, `LLMGATEWAY_API_KEY`), sent only to that domain over https. Other hosts need `ALLOW_ANY_UPSTREAM` (default on only for a loopback `HOST`).
- Without `server.js` (GitHub Pages), the page finds no `config` and calls the base URL directly. Requesty and OpenRouter allow CORS; LLM Gateway does not (no `Access-Control-Allow-Origin`, checked 2026-11-09), so its file has `needsServer: true`: on a static page it is greyed out in the picker and its sign-up link is shown in the top bar instead. A provider file's `categorize` (`field` plus `order` of [value, tab]) decides a model's tab when its list has no endpoints or `api` field, as LLM Gateway's `architecture.output_modalities`. LLM Gateway's spec is `docs/llmgateway-openapi.json`. `llmgateway-self.json` is a self-hosted LLM Gateway (github.com/theopenco/llmgateway): it `extends` `llmgateway.json` (a provider file can start from another and override keys) without `needsServer`, since its operator can allow the page's origin (`GATEWAY_CORS_ORIGINS`). Both have `attributionHeaders: false`, so direct calls skip `HTTP-Referer`/`X-Title`, which LLM Gateway's CORS does not allow. Keep every path in `public/` relative so it works from the `/LLM-PlayGround/` subfolder.
- Workflows: `docker.yml` pushes `ghcr.io/hkarn/llm-playground` on `main`; `pages.yml` publishes `public/` to Pages and adds `?v=<commit>` to `js/main.js` and `style.css` in `index.html` and to every `from '….js'` import in `public/js/`, and writes the commit into `ASSET_VERSION` in `core.js` (data files are fetched with `?v=ASSET_VERSION`), so keep those as plain relative paths (`'./core.js'`, `'../core.js'`) and import a module by the same path everywhere.
- The UI is plain JS ES modules in `public/js/` (no build step), loaded from `index.html` as `js/main.js`. `ui/dom.js` (`$`, `$$`, `el`) imports nothing; `core.js` (providers, `callApi`, cURL, the models list, storage, form and text helpers) imports only `ui/dom.js`; `adapter.js` (request templates and response maps) imports only core; `ui/*.js` are reusable components (`result.js` result panel and images, `model-picker.js`, `model-options.js`, `run-step.js` Send/Cancel and `wait`, `drafts.js`, `remember.js`, `tool-layout.js` settings panel, `combo.js` the text field with a page-drawn suggestion list (model filter, AI Group Chat; use it instead of `<datalist>`, which only offers entries matching what is already typed), `copy-button.js`, `ref-portraits.js` named reference images, `theme.js` the Auto/Light/Dark toggle (`theme` in localStorage, `data-theme` on `<html>`, applied before paint by the inline script in `index.html`; dark colours are defined twice in `style.css`, under the system's dark setting and under `[data-theme=dark]`, so a new colour goes in both), `top-bar.js` the pinned top bar that keeps to one line: it drops `.opt` words, then folds the tabs into a drop-down, then trims the chip, and wraps unpinned only when nothing else fits); `testers.js` holds the endpoint tabs (one handler per tab in `handlers`, a deliberately plain raw debugger); `apps/<app id>.js` is one file per tool or game; `providers-guide.js` (the Welcome page, imports core and dom; main passes it the app cards), `hubs.js` (launcher, `APPS`, direct links) and `main.js` (start-up) sit on top. Imports run one way (dom ← core ← adapter ← ui ← testers/apps ← hubs ← main); core announces a new model list with the `models-changed` event instead of importing the pickers. Keep each new tool in its own `apps/` file and build it from `ui/` components; move anything a second app needs into `ui/`. Every send goes through `runStep`, which shows a Cancel button and aborts through `form._abort`; pass `signal: form._abort?.signal` to every `callApi` (and use `wait()` between polls). No request timeouts: slow providers are part of the test. Typed text survives a reload via `keepDrafts`/`keepRows` (sessionStorage); model and option choices via `rememberModel` (localStorage, per provider).
- Games and Tools tabs are hubs: `APPS.games` / `APPS.tools` in `hubs.js` list apps as `{ id, title, blurb, icon, status?, render(container) }`; `setupHubs` draws the icon launcher and opens an app full-page under the tab bar, with a header pinned under the top bar: a back button and the app's title as a drop-down of every app in the hub (`appSwitcher`); its height is `--apphead-h`, which the tools' sticky settings panel adds to its top. Direct links are the hash: `#<tab>`, `#<hub>` or `#<hub>/<app id>` (`route()`, `setHash`); an app's `id` is its URL, so don't rename one. Animate the DreamGen Scene (`dreamgen-video`) takes its first frame from Draw the DreamGen Scene through `ui/scene-handoff.js` (in memory only, with the image prompt and session text), or an upload; a chat model writes the motion prompt from the same session export (`MOTION_SYSTEM_PROMPT`), and the clip uses the same tested models and `ui/video-*.js` as the Video Generator. Both DreamGen tools read exports with `ui/dreamgen-export.js` and share the picture styles in `ui/scene-styles.js` (one remembered choice, added to the end of the image or motion prompt as "Style: …"). The Video Generator (`apps/video-generator.js`) makes clips with the tested models in a provider file's `videoModels` (OpenRouter's: options, audio behaviour, faces, what each test run cost), built from `ui/video-settings.js` (the model list: one row per model with marks for start/end picture, sound and a face kept, from the file's `frames`, `audio` and `faces`, and a legend; per-model options, price from `pricing_skus` via `estimateVideoCost`) `ui/video-job.js` (`submitVideoJob` and `watchVideoJob`: submit, then poll and download from the id alone, through the adapter's `video` kind; frames other than PNG/JPEG go as PNG via `ui/frame-image.js`) and `ui/video-jobs.js` (both video tools start clips with `startVideoJob`, which saves the job in `tools:videojobs` (no media) and watches it in the background, so the form is free at once, jobs run while you use other pages, and `startWatchingVideoJobs` in main picks unfinished ones up after a reload, on the provider that made them only; the list is the Video jobs section of each video tool's settings panel, and replaced the Video Generator's own clip list `videogen:jobs`; the Video tab, the raw tester, doesn't use it). AI Group Chat (`apps/group-chat.js`) is a working prototype: ticked characters answer in a queue each round, ordered by a strategy in `GC_ORDER` (random, list order, or `decision`: a `choice` question to the provider's decisions endpoint through the adapter, options = the ticked characters with their personas, never the player, minus the last speaker on a passed round, who counts as 0 % and goes last; a strategy may return `{ order, odds, cost }`, odds shown on the queue chips; a failure falls back to random with a note; the decision model is kept per provider in `decisionModels`); a failed reply has a retry (↻) that asks again in place with the history before it, and its state is kept in `localStorage` under `groupchat`. Draw the DreamGen Scene (`renderDreamGenScene`) sends a whole DreamGen session export as Markdown (JSON is written out in the same layout; the user can edit it down to save tokens), has a chat model find the last scene and write an image prompt for it, then draws it with optional named reference portraits as an `imageEdit` through the adapter; format in `docs/dreamgen-session-export.md`. Apps build their own forms and pickers (not `.request-form`), so `setupHubs` runs after the tab pickers; A tool with one model of each kind lays out with `toolLayout` (`ui/tool-layout.js`): its models, their options, the picture style and advanced bits (system prompt, max tokens) in a settings panel on the right (a Settings button above the steps on a narrow screen), and the steps, with what changes each run, the price line and the spending button, in the main column on the left; the tool's How it works and privacy text goes in `aboutBox(id, …)`, open on the first visit and folded after. Tool pages use a larger type size than the testers (`.tool-layout` in `style.css`). Its settings are separate forms in the panel that the steps read. The choice per kind is shared by every tool, per provider: `rememberModel(form, 'chat' | 'image', …)` and `videoSettings()` (`tools:video`), so a new tool must use those keys. The tools render results with `renderResult(…, { quiet: true })`, which folds the status and raw views into "Request details"; the API tester tabs and AI Group Chat keep their own layout. The tool's privacy note (nothing leaves the browser except the user's own requests to their provider) must stay true: no analytics, no outside resources, no logging of content in `server.js`. Add a video model to `videoModels` only after a real run, with what it cost; the Video tab stays the raw tester for every video model.
- The Requesty API source of truth is `docs/requesty-inference-openapi.json`. Check request and response formats there before changing a handler. Put specs for new providers in `docs/` too.
- OpenRouter: `/models` only lists text models unless `output_modalities=all`. Each model's `endpoints` array decides its tab. `/images/models` (per-model `supported_parameters` enums; a missing key = unsupported) and `/videos/models` (`supported_durations` etc.) are merged in by id. Speech voices are in `supported_voices`; `/audio/speech` returns only mp3 or pcm. Pricing is `pricing.prompt`/`completion` as strings per token.
- OpenRouter paths: decisions at `/api/alpha/decisions` (same format as Requesty, alpha); images and image edits both `POST /api/v1/images` (JSON, edits as `input_references` data URLs, no mask, response `b64_json` + `media_type`; the edit template is in `openrouter.json`); video is async: `POST /videos` → poll `GET /videos/{id}` → `GET /videos/{id}/content?index=0`; rerank `{model, query, documents, top_n}` → `results[{index, relevance_score, document}]`. `/embeddings/models` has no CORS.
- Top bar (`index.html`, wired in `main.js`): Providers, Games and Tools tabs; an API tester toggle (followed by the Filter models tab, `#models`) that opens the last endpoint tab (`testerTab` in localStorage), and the endpoint tabs (`#tester-tabs`) show as a second row only while one of them is open (`showTab` in `hubs.js`). The provider, base URL and key live in a panel behind the connection chip, which shows provider · host and the model status read from `#models-status`; it turns green only with a key (typed, or a server key) as well as a model list, since OpenRouter's and Requesty's lists are public. Without a key, Load models is disabled and `loadModels` refuses (`keyReady()` in core). Its "No key?" line links the default (easiest) provider and every provider whose `signup` has `"referral": true`.
- Docs for people: `README.md` is the friendly start (what it is, a key, running it locally); `docs/guides/<tool>.md` is a step-by-step user guide per tool or game; `docs/providers.md`, `docs/running.md` and `docs/code.md` are the reference, indexed in `docs/README.md`. When a change alters what a user sees or does, update the matching guide in the same PR.
- Keep it dependency-free: no build step and no npm packages.

## Issues: what is planned, in progress and left over
- Every change starts from an issue. Before a branch, find the issue or open one, then link the PR to it: `Closes #N` in the PR body (or `Part of #N` when the PR is one step of a larger issue, and say which step), so the merge closes it. A PR that is one step leaves its issue open, with the step ticked in the issue's checklist.
- Small UI fixes are batched. A spacing, colour, wording, alignment or similar tweak (often asked for in passing) doesn't get its own issue: add it as a checkbox to the one open issue titled "Small UI fixes" (open it, labelled `enhancement`, if there is none), with where it is and what's wrong. Fix the list in one PR when the owner asks or the list has grown, tick each box it covers, and use `Closes #N` once every box is ticked. Anything that changes behaviour, needs a decision or is more than a few lines still gets its own issue.
- Leftovers become issues before work is reported done: an untested path, a follow-up, a review finding not fixed in its PR, a step the session could not do, a proposal waiting for the owner. The reply to the owner links them. A chat summary is not a record.
- Write an issue for someone without this session's context: the files and functions involved, how it works today, what done looks like, and the open questions. A large issue gets a checklist of PR-sized steps.
- Labels: `enhancement` (new or changed behaviour), `bug`, `documentation`, `question` (a proposal or choice waiting for the owner's decision; say "Waiting for the owner's decision" at the top). Don't create labels without asking.
- Close an issue that was done outside a PR, or no longer applies, with a short comment saying why and the right reason (completed or not planned). Never close the owner's issues on a bot's say-so.

## How changes land (pull requests)
- `main` is protected: no direct pushes and no force pushes. Every change is a pull request from a branch made from the latest `main`; CI (`build` in `docker.yml`) must pass.
- Sync first, every time: nothing fetches by itself, and a local `main` can be many merges behind GitHub. Before reading code for a task or making a branch, run `git fetch origin` and `git switch main && git pull --ff-only`, then branch. Before pushing more work to an existing branch, `git fetch origin` and merge `origin/main` into it if it is behind (a merge, never a rebase of pushed commits). If `git pull --ff-only` fails because local `main` has its own commits, stop and ask the owner.
- One topic per PR, linked to its issue (see above). Split large refactors into steps that each leave the app working and can be read on their own (for example: move code unchanged first, change behaviour after).
- Open PRs as drafts. The owner marks a PR ready for review, which starts the Copilot review, and the owner merges (squash). Merge for them only when they ask.
- Review comments, from Copilot or a person: check each claim against the code first. Fix what is real in a new commit, and reply on the thread with what you found and what changed (or why nothing did). Leave resolving threads to the owner. Points a review summary mentions without a thread get the same check, reported to the owner.
- Before pushing: `node --check` every changed `.js` file and parse every changed `.json` file; open the page and use what changed (tabs, tools, a reload, a provider switch) with the provider mocked; for refactors, send the same scenarios from the old and the new page and compare the requests. Say in the PR what was tested and what was not (for example: no real provider call).
- The built-in browser pane's saved state (provider choice, chats, video jobs, settings in its localStorage) is a scratch session, not the owner's: change it freely for a test (switch provider, add test data, reload) and don't back it up or restore it afterwards. Spending money or sending real requests still needs the owner's go-ahead.
- After a squash merge, start the next branch from the new `main`. Never rewrite pushed history; if a branch name is reused, merge its old remote history in with a merge commit that changes no files.
- Commit messages and PR descriptions say what changed and why, and what it means for someone using the page.

## Where the live Requesty API differs from the spec
Found by testing with a real key; keep handling both shapes.
- Decision `score` answers: `probabilities` is an object keyed by index (`"0"`…), with a `legend` mapping index → label. `score` is the expected index.
- Only chat models have `input_price`/`output_price`/`context_window`. Others have a `pricing` object of per-unit keys (`input_character`, `input_second`, `output_image`, …). Chat `pricing` is an array of tiers.
- Speech: non-OpenAI models (e.g. DeepInfra MiMo) return `500 [provider]` for OpenAI voice names like `alloy`. Leaving the voice out works. `/models/all` has no voice names, so `public/providers/speech-voices.json` lists them per model (a `match` pattern on the model id), taken from each provider's docs. Update it when Requesty adds speech models.
- Transcriptions also return `language`, `duration` and `segments`. DeepInfra models can take about a minute on a cold start.

## The @claude workflow on GitHub
- A `@claude` mention in an issue runs `.github/workflows/claude.yml`, which is read-only. Only when running in that workflow (the prompt says you are helping with a GitHub issue, and Bash/Edit/Write are denied): review the issue against the code on `main`; if it's already done or no longer applies, say so and suggest closing it; otherwise reply with a concrete plan (files, steps, tests owed, open questions). Don't try to change files or push there. Every other session, wherever it runs, works on issues as usual.
- Copilot reads `.github/copilot-instructions.md`, which points to this file; keep the rules here, not there.
