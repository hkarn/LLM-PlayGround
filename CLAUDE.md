# LLM PlayGround

A web playground for LLM providers and routers, plus a place for small LLM-based experiments such as games. Live at https://hkarn.github.io/LLM-PlayGround/. Forked by copy from requesty-tester. Endpoints so far: Requesty, OpenRouter, LLM Gateway (hosted), a self-hosted LLM Gateway and a custom OpenAI-compatible URL.

- Run: `node server.js` (Node 18+, no dependencies), then open http://127.0.0.1:3000. Docker: `docker compose up`.
- Endpoints are settings files, one per provider: `public/providers/<id>.json` (order in `providers/index.json`), loaded at start-up by `loadProviders()` into `PROVIDERS` in `public/js/core.js`. Each has `label`, suggested `baseUrl`, `modelsPaths`, `keyEnv`, `keyHint`, `signup`, `server.domain`, `unsupported` tabs, per-tab `endpoints` overrides (`path` and `base: {replace: [pattern, with]}` read by `ep(kind)`, and the request/response template keys read by `adapter.js`), `suggest` lists, `guide` (the Providers tab card: setup `level` 1-4, `ease`, `summary`, `steps`, `good`, `watch`) and `speechVoices` (a voice-list file in `providers/`, e.g. the shared `speech-voices.json`); comments go in `_notes`. Hardcoded, provider-specific data belongs in these files, not in code. Greyed tabs: Requesty rerank/video; Custom decision/rerank/video (no OpenAI standard). A new provider is a new file plus its id in `index.json`. The first provider in `index.json` that works on the page (OpenRouter: Google sign-in, credit, key, every model on) is the default for a new visitor; a saved choice wins. The page opens on the Providers tab (`providers-guide.js`), which explains each provider's setup and holds the sign-up and referral links. Requests and answers go through `public/js/adapter.js`: `send(kind, input)` fills the endpoint's `request` template (shared OpenAI-standard shapes in `providers/openai-standard.json`, named as `templates` in `index.json`; a provider's `endpoints.<kind>` replaces keys of it) and `read(kind, resp)` maps the answer to the app's own terms (`text`, `images[]`, `usage`, …) through its `response` map. Template rules are in the `_notes` of `openai-standard.json`. Every kind goes through it: chat, decision, embeddings, rerank, image, imageEdit, video, speech and transcription (all tester tabs, Draw the DreamGen Scene, AI Group Chat). A File inside an input is sent as a data URL in JSON bodies (shown as a placeholder); an async job's follow-up GETs are `poll`/`content` path templates sent with `follow(kind, step, vars)` (video). Never build a provider's wire format in an app.
- Dropdowns follow the model (`setupModelOptions`): model metadata first, then the provider's `suggest` list (`false` = not supported), then the options in `index.html`. Disabled fields are never sent (`str`/`num` skip them). Add hardcoded suggestions only where no API list gives the choices. The base URL field is editable; each provider keeps its own key and edited URL in `localStorage`.
- `server.js` serves `public/` and proxies `/api/*` to the `X-Upstream-Base` header the page sends. It reads the same provider files: a provider with `server.domain` and `keyEnv` gets a server key from that env var (`REQUESTY_API_KEY`, `OPENROUTER_API_KEY`, `LLMGATEWAY_API_KEY`), sent only to that domain over https. Other hosts need `ALLOW_ANY_UPSTREAM` (default on only for a loopback `HOST`).
- Without `server.js` (GitHub Pages), the page finds no `config` and calls the base URL directly. Requesty and OpenRouter allow CORS; LLM Gateway does not (no `Access-Control-Allow-Origin`, checked 2026-11-09), so its file has `needsServer: true`: on a static page it is greyed out in the picker and its sign-up link is shown in the top bar instead. A provider file's `categorize` (`field` plus `order` of [value, tab]) decides a model's tab when its list has no endpoints or `api` field, as LLM Gateway's `architecture.output_modalities`. LLM Gateway's spec is `docs/llmgateway-openapi.json`. `llmgateway-self.json` is a self-hosted LLM Gateway (github.com/theopenco/llmgateway): it `extends` `llmgateway.json` (a provider file can start from another and override keys) without `needsServer`, since its operator can allow the page's origin (`GATEWAY_CORS_ORIGINS`). Both have `attributionHeaders: false`, so direct calls skip `HTTP-Referer`/`X-Title`, which LLM Gateway's CORS does not allow. Keep every path in `public/` relative so it works from the `/LLM-PlayGround/` subfolder.
- Workflows: `docker.yml` pushes `ghcr.io/hkarn/llm-playground` on `main`; `pages.yml` publishes `public/` to Pages and adds `?v=<commit>` to `js/main.js` and `style.css` in `index.html` and to every `from '….js'` import in `public/js/`, and writes the commit into `ASSET_VERSION` in `core.js` (data files are fetched with `?v=ASSET_VERSION`), so keep those as plain relative paths (`'./core.js'`, `'../core.js'`) and import a module by the same path everywhere.
- The UI is plain JS ES modules in `public/js/` (no build step), loaded from `index.html` as `js/main.js`. `ui/dom.js` (`$`, `$$`, `el`) imports nothing; `core.js` (providers, `callApi`, cURL, the models list, storage, form and text helpers) imports only `ui/dom.js`; `adapter.js` (request templates and response maps) imports only core; `ui/*.js` are reusable components (`result.js` result panel and images, `model-picker.js`, `model-options.js`, `run-step.js` Send/Cancel and `wait`, `drafts.js`, `remember.js`, `settings-toggle.js`, `copy-button.js`, `ref-portraits.js` named reference images); `testers.js` holds the endpoint tabs (one handler per tab in `handlers`, a deliberately plain raw debugger); `apps/<app id>.js` is one file per tool or game; `providers-guide.js` (the Providers tab, imports core and dom), `hubs.js` (launcher, `APPS`, direct links) and `main.js` (start-up) sit on top. Imports run one way (dom ← core ← adapter ← ui ← testers/apps ← hubs ← main); core announces a new model list with the `models-changed` event instead of importing the pickers. Keep each new tool in its own `apps/` file and build it from `ui/` components; move anything a second app needs into `ui/`. Every send goes through `runStep`, which shows a Cancel button and aborts through `form._abort`; pass `signal: form._abort?.signal` to every `callApi` (and use `wait()` between polls). No request timeouts: slow providers are part of the test. Typed text survives a reload via `keepDrafts`/`keepRows` (sessionStorage); model and option choices via `rememberModel` (localStorage, per provider).
- Games and Tools tabs are hubs: `APPS.games` / `APPS.tools` in `hubs.js` list apps as `{ id, title, blurb, icon, status?, render(container) }`; `setupHubs` draws the icon launcher and opens an app full-page under the tab bar. Direct links are the hash: `#<tab>`, `#<hub>` or `#<hub>/<app id>` (`route()`, `setHash`); an app's `id` is its URL, so don't rename one. Video Generator and Animate the DreamGen Scene (`dreamgen-video`; it will take its first frame from Draw the DreamGen Scene and its motion from the same session export) are layout placeholders so far. AI Group Chat (`apps/group-chat.js`) is a working prototype: ticked characters answer in a queue each round, ordered by a strategy in `GC_ORDER` (random or list order; the place to plug in a ranking model), and its state is kept in `localStorage` under `groupchat`. Draw the DreamGen Scene (`renderDreamGenScene`) sends a whole DreamGen session export as Markdown (JSON is written out in the same layout; the user can edit it down to save tokens), has a chat model find the last scene and write an image prompt for it, then draws it with optional named reference portraits as an `imageEdit` through the adapter; format in `docs/dreamgen-session-export.md`. Apps build their own forms and pickers (not `.request-form`), so `setupHubs` runs after the tab pickers; `rememberModel` and `settingsToggle` keep a tool step's model and options per provider and fold its settings once the model is chosen. The tool's privacy note (nothing leaves the browser except the user's own requests to their provider) must stay true: no analytics, no outside resources, no logging of content in `server.js`. Video Generator is meant to list only video models whose options we have tested; the Video tab stays the raw tester.
- The Requesty API source of truth is `docs/requesty-inference-openapi.json`. Check request and response formats there before changing a handler. Put specs for new providers in `docs/` too.
- OpenRouter: `/models` only lists text models unless `output_modalities=all`. Each model's `endpoints` array decides its tab. `/images/models` (per-model `supported_parameters` enums; a missing key = unsupported) and `/videos/models` (`supported_durations` etc.) are merged in by id. Speech voices are in `supported_voices`; `/audio/speech` returns only mp3 or pcm. Pricing is `pricing.prompt`/`completion` as strings per token.
- OpenRouter paths: decisions at `/api/alpha/decisions` (same format as Requesty, alpha); images and image edits both `POST /api/v1/images` (JSON, edits as `input_references` data URLs, no mask, response `b64_json` + `media_type`; the edit template is in `openrouter.json`); video is async: `POST /videos` → poll `GET /videos/{id}` → `GET /videos/{id}/content?index=0`; rerank `{model, query, documents, top_n}` → `results[{index, relevance_score, document}]`. `/embeddings/models` has no CORS.
- Keep it dependency-free: no build step and no npm packages.

## Issues: what is planned, in progress and left over
- Every change starts from an issue. Before a branch, find the issue or open one, then link the PR to it: `Closes #N` in the PR body (or `Part of #N` when the PR is one step of a larger issue, and say which step), so the merge closes it. A PR that is one step leaves its issue open, with the step ticked in the issue's checklist.
- Leftovers become issues before work is reported done: an untested path, a follow-up, a review finding not fixed in its PR, a step the session could not do, a proposal waiting for the owner. The reply to the owner links them. A chat summary is not a record.
- Write an issue for someone without this session's context: the files and functions involved, how it works today, what done looks like, and the open questions. A large issue gets a checklist of PR-sized steps.
- Labels: `enhancement` (new or changed behaviour), `bug`, `documentation`, `question` (a proposal or choice waiting for the owner's decision; say "Waiting for the owner's decision" at the top). Don't create labels without asking.
- Close an issue that was done outside a PR, or no longer applies, with a short comment saying why and the right reason (completed or not planned). Never close the owner's issues on a bot's say-so.

## How changes land (pull requests)
- `main` is protected: no direct pushes and no force pushes. Every change is a pull request from a branch made from the latest `main`; CI (`build` in `docker.yml`) must pass.
- One topic per PR, linked to its issue (see above). Split large refactors into steps that each leave the app working and can be read on their own (for example: move code unchanged first, change behaviour after).
- Open PRs as drafts. The owner marks a PR ready for review, which starts the Copilot review, and the owner merges (squash). Merge for them only when they ask.
- Review comments, from Copilot or a person: check each claim against the code first. Fix what is real in a new commit, and reply on the thread with what you found and what changed (or why nothing did). Leave resolving threads to the owner. Points a review summary mentions without a thread get the same check, reported to the owner.
- Before pushing: `node --check` every changed `.js` file and parse every changed `.json` file; open the page and use what changed (tabs, tools, a reload, a provider switch) with the provider mocked; for refactors, send the same scenarios from the old and the new page and compare the requests. Say in the PR what was tested and what was not (for example: no real provider call).
- After a squash merge, start the next branch from the new `main`. Never rewrite pushed history; if a branch name is reused, merge its old remote history in with a merge commit that changes no files.
- Commit messages and PR descriptions say what changed and why, and what it means for someone using the page.

## Where the live Requesty API differs from the spec
Found by testing with a real key; keep handling both shapes.
- Decision `score` answers: `probabilities` is an object keyed by index (`"0"`…), with a `legend` mapping index → label. `score` is the expected index.
- Only chat models have `input_price`/`output_price`/`context_window`. Others have a `pricing` object of per-unit keys (`input_character`, `input_second`, `output_image`, …). Chat `pricing` is an array of tiers.
- Speech: non-OpenAI models (e.g. DeepInfra MiMo) return `500 [provider]` for OpenAI voice names like `alloy`. Leaving the voice out works. `/models/all` has no voice names, so `public/providers/speech-voices.json` lists them per model (a `match` pattern on the model id), taken from each provider's docs. Update it when Requesty adds speech models.
- Transcriptions also return `language`, `duration` and `segments`. DeepInfra models can take about a minute on a cold start.
